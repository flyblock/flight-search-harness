# Round-trip Product Kernel workflow

Use this reference for round-trip product decisions. The resolver's `mission_runtime_ref` provides the shared Search Mission lifecycle, Receipt format, recovery procedure, and Outcome handling.

## Inputs and defaults

Capture the origin and destination `anchor_nodes` and optional `seed_gateway_nodes`, `outbound_departure_window`, `return_departure_window`, traveler count, accepted modes, Base Currency, `fx_to_base`, the shared baggage policy, overnight and self-transfer policies, and any hard budget, duration, destination-stay, connection, or accessibility constraints. Any non-Base-Currency rate or money value requires a matching source-attributed `fx_snapshot` that is current at Run start and completion.

Preserve `exact_dates`, `bounded_window`, or `fully_flexible` independently for outbound and return research. Apply minimum or maximum stay limits only when the user supplies them. Include unavoidable intermediate lodging unless the user explicitly excludes a discretionary stay.

## Search decisions

- For each non-exact regional side, complete both the semantic `region_scope_definition` and the independent `region_scope_challenge`. The admitted union, not a static airport map or the request seeds alone, defines the bounded gateway scope.
- The round-trip Provider foundation excludes AZair. Google Flights is the binding first flight attempt only when a verified query shape represents the Work Item's actual scope. Otherwise begin with a capability-matched Provider.
- Keep every payable ticket atomic. For an ordinary closed pair, research the joint round-trip quote first as an observed baseline, then cover both split directions. The Product Kernel may also publish Evidence-backed open-jaw, nested, multi-city, mixed, or surface-supported portfolio challengers.
- Keep round-trip frontier state product-local. Activate or dismiss Product Kernel-published portfolio or structural challengers with a concrete reason.
- Flexible-date calendar or grid signals are research-only. Choose a hard-valid date pair through a published temporal action, then verify a concrete payable Offer on the same Work Item.

## Evidence

A priced movement needs current visible Evidence with exact endpoints, offset-aware schedule, service identity, seller or operator, URL, observation time, baggage terms, mandatory amount for the declared traveler party, and currency. Joint, multi-city, and nested ticket totals are indivisible; never invent directional or component prices.

Keep physical movements separate from atomic Offers and count every selected Offer once. Surface legs require their own operator or seller Evidence. A short same-ticket connection is protected only when payable Evidence establishes a protected through-ticket; shared pricing, matching carrier names, or the absence of a warning is not enough.

Research-only, topology, calendar, historical, estimated, unknown, no-result, rejected, or expired Observations cannot become current priced movements. Strict live multi-currency comparison requires explicit current FX Evidence.

## Completion

Completion requires both regional-scope passes when applicable, terminal research for every admitted gateway, terminal gateway hypotheses, a verified complete portfolio, coverage of its mandatory atomic questions, resolution of published structural and portfolio challengers, no unexplained pending work, and a fresh stop assessment after the latest change.

Report the winning city-to-city portfolio first, followed by chronological movements, waits, atomic ticket boundaries, sellers, surface access or egress, entitlements, mandatory totals, baggage, elapsed time, and materially different verified alternatives. Disclose unsearched gateway, date, Provider, and portfolio scope, and describe the result as the best verified portfolio within that scope.
